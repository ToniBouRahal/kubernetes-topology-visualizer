# ADR-014: Security Hardening — Authenticated Access, Mutual TLS, Least Privilege

- **Status:** Accepted for implementation
- **Date:** 2026-09-30
- **Parent:** ADR-001 §13 (two deferred items taken into scope: "authentication and role-based UI
  access" and "capability-based agent hardening without privileged mode") · §6 (privacy, least
  privilege)
- **Amends:** ADR-002 (agent privilege, transport), ADR-003 (ingestion is authenticated),
  ADR-004 D-4.6 (listeners, headers), ADR-005 (database connections use TLS), ADR-006 (the UI sits
  behind a login), ADR-007 D-7.4 (security posture), D-7.5 (`tls.*`, `auth.*`), ADR-008 (CI
  security scanning)
- **Component path:** `charts/topology-visualizer/`, `backend/app/`, `agent/internal/`,
  `frontend/default.conf.template`, `.github/workflows/ci.yml`
- **Owning phase:** Post-Phase-5 extension

## 1. Context

The system's output is a map of which workloads talk to which. That map is sensitive: it is the
reconnaissance an attacker inside a cluster would otherwise have to do. The Phase 5 security review
(P5-T19) was clean within the accepted scope, but that scope deliberately left three doors open:

| # | Gap | Today | Stated in |
|---|---|---|---|
| G1 | **Anyone who reaches the frontend or backend Service reads the whole topology.** The only gate is who may `kubectl port-forward`. | no authentication | ADR-001 §13 |
| G2 | **Any pod that reaches the ingest port can write fabricated topology.** A NetworkPolicy narrows who can connect, but only under an enforcing CNI, and kind's does not enforce. | unauthenticated ingest | `limitations.md` §4.4 |
| G3 | **All in-cluster traffic is plaintext**: agent → backend, frontend → backend, backend → PostgreSQL. | HTTP / plain PG | — |
| G4 | **The agent runs `privileged: true` with `hostPID: true`**, far more than loading one BPF program needs. | privileged | ADR-001 §13 |
| G5 | **No browser security headers** (CSP, framing, sniffing, referrer). `server_tokens` on. FastAPI's `/docs` and `/redoc` enabled. | defaults | — |
| G6 | **No dependency or image vulnerability scanning in CI**; Actions pinned by tag, not commit. | none | — |

The project's owner asked to close all of them. Authentication and agent de-privileging are
deferred items, so this ADR takes them into scope before any code (ADR-001 §12 instruction 6).

### Threat model

| Actor | Can | Must not be able to |
|---|---|---|
| A workload in the cluster (compromised pod) | reach Services by network | read topology, write topology, reach PostgreSQL |
| A person with network reach to the UI but no account | load the login page | see anything else |
| A signed-in user | read topology for any period | write topology; reach the ingest path |
| An agent | submit batches | read topology |
| Someone with node root | everything on that node | — (out of scope: node root owns the kernel the agent observes) |

## 2. Decision

**D-14.1 — Secure by default.** TLS is always on in the chart; there is no switch to turn it off.
Authentication is on by default (`auth.enabled: true`); turning it off is an explicit, documented
choice that the chart's NOTES warn about. A backend run outside the chart with no TLS settings (unit
tests, `vite` development) serves one plain listener as today and logs a warning at start-up.

**D-14.2 — An internal PKI with one CA per role.** Three CAs, each trusted for exactly one thing:

| CA | Signs | Trusted by |
|---|---|---|
| `server` | backend, PostgreSQL and bundled-Dex server certificates | agent, frontend (nginx and oauth2-proxy), backend (as a PostgreSQL client) |
| `ingest-client` | agent client certificate | the backend's ingest listener only |
| `api-client` | frontend client certificate | the backend's API listener only |

One CA per role is how authorisation is enforced without the application inspecting certificates:
uvicorn can *require* a client certificate but does not expose which one connected, so the ingest
listener simply cannot complete a handshake with a frontend certificate, and vice versa.
Certificates are generated by the chart (`genCA`/`genSignedCert`) and persisted across upgrades
with `lookup`, so the offline kind demo needs no cert-manager. An operator may supply their own
Secrets instead (`tls.existingSecrets`, e.g. populated by cert-manager). Leaf certificates are valid
for 365 days; rotation is documented (delete the Secrets, upgrade; pods roll on the checksum).

**D-14.3 — Three backend listeners, each with one job.**

| Listener | Port | TLS | Serves | Reached by |
|---|---|---|---|---|
| ingest | 8443 | mTLS, `ingest-client` CA | `POST /api/v1/ingest/batches` only | agent pods |
| api | 8444 | mTLS, `api-client` CA | `GET /api/v1/*` only | frontend pods |
| ops | 8000 | plain | `/health/*`, `/metrics` only | kubelet probes, Prometheus |

A request for a path outside a listener's list is `404` on that listener. `/metrics` carries
counters, never topology. The NetworkPolicy admits each port from its one client.

**D-14.4 — The agent authenticates with its client certificate** and verifies the backend's server
certificate against the `server` CA, by Service DNS name. Its batch format is unchanged (ADR-003).

**D-14.5 — The frontend's nginx reaches the backend over mTLS** with the `api-client` certificate,
verifying the backend. `POST` to the ingest path through nginx is no longer possible: the API
listener does not serve it.

**D-14.6 — Sign-in with OIDC through oauth2-proxy.** An oauth2-proxy sidecar in the frontend pod;
nginx gates **every** path except `/oauth2/*` and `/healthz` with `auth_request`. Any OIDC provider
works (`auth.oidc.issuerUrl`, `clientId`, client secret from a Secret). Authorisation: optional
`auth.oidc.allowedEmailDomains` and `allowedGroups`; the application is read-only, so a signed-in,
allowed user has one role, *viewer*. Session cookie: `Secure`, `HttpOnly`, `SameSite=Lax`,
8-hour lifetime, secret generated by the chart. The signed-in user's e-mail is forwarded to the
backend and written to the request log; the backend trusts that header only on the API listener,
whose only client is nginx.

**D-14.7 — A bundled Dex for the kind demo.** `auth.dex.enabled` (default `false`; `true` in the
kind values) installs Dex as a subchart with one static user whose password is generated into a
Secret. Dex is served under `/dex` through the frontend, so the demo still needs **one**
port-forward. oauth2-proxy skips discovery and uses split URLs: the browser-facing issuer
(`http://localhost:8080/dex`) and in-cluster token and key endpoints. **Dex serves HTTPS** with a
`server`-CA certificate, and both nginx and oauth2-proxy verify it: the token exchange carries the
client secret and the sign-in code, so it is not left in the clear. Its chart also always opens
plain HTTP, with no switch to remove it; a NetworkPolicy admits only the frontend, on HTTPS
(`limitations.md` §6.2). oauth2-proxy runs with `--approval-prompt=auto`: its default forces a
consent screen on every sign-in, which Dex's `skipApprovalScreen` cannot override.

**D-14.8 — PostgreSQL requires TLS.** The in-cluster database serves TLS with a `server`-CA
certificate and accepts only `hostssl` connections; the backend connects with
`sslmode=verify-full`. An external database's TLS is the operator's (`postgresql.mode: external`).

**D-14.9 — The agent runs with capabilities, not privilege.** `privileged: false`,
`hostPID: false`, all capabilities dropped and only `BPF` and `PERFMON` added, read-only root
filesystem, plus whatever else is **measured** as necessary on the target kernel and recorded with
its reason. `agent.privileged: true` remains as an escape hatch for kernels without `CAP_BPF`
(before 5.8, outside ADR-002's support range anyway).

*Measured (kind, kernel 6.8):* nothing else was necessary. `BPF` + `PERFMON`, the runtime's default
seccomp profile (previously asserted to break capture — true under `privileged` on the Phase 5
setup, not with real capabilities), no `hostPID`, no BPF filesystem, and `/sys/kernel/tracing` as
the one host path, read-only. The counted burst reports exactly 100 of 100.

**D-14.10 — HTTP hardening.** nginx: `Content-Security-Policy` (`default-src 'self'`; styles
allow `'unsafe-inline'` because React Flow positions nodes with inline styles; `frame-ancestors
'none'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, a restrictive
`Permissions-Policy`, `server_tokens off`, a request-rate limit on `/api/`. Backend: `/docs` and
`/redoc` disabled.

**D-14.11 — Supply chain in CI.** `govulncheck`, `pip-audit`, `npm audit --omit=dev`, a Trivy scan
of the three built images failing on fixable HIGH/CRITICAL findings, and a CycloneDX SBOM per image
uploaded as a build artifact. Every GitHub Action pinned to a commit SHA. **Image signing is not
done**: this project never publishes images to a registry (kind side-loads them), so there is
nothing a signature would protect; recorded as a limitation, not claimed.

**D-14.12 — Namespace Pod Security.** The agent still needs a host path and two capabilities, which
the `baseline` Pod Security Standard forbids, so the release namespace is labelled
`enforce: privileged` and `warn`/`audit: restricted` by the demo tooling (`make pod-security`), and
the operator guide says why. *Measured by server dry run:* every other workload — backend, frontend
and oauth2-proxy, PostgreSQL, Dex — already meets `restricted`. Moving the agent to its own
namespace is the lift, and is not taken here.

## 3. Consequences

- The kind demo gains a sign-in step (Dex, one generated user). The E2E suite signs in first.
- `make demo-up` still needs one port-forward, but everything behind it now needs a session.
- The backend holds three certificates and runs three listeners; its probes move to the ops port.
- Ingest and API traffic is encrypted and mutually authenticated; G2 closes without depending on
  the CNI enforcing NetworkPolicy.
- Unit tests and local development keep a single plain listener (D-14.1).
- Certificates expire after a year; the operator guide covers rotation.

## 4. Alternatives rejected

- **Kubernetes ServiceAccount tokens for ingest** (TokenReview): no certificates to manage, but no
  encryption, and the backend would need API-server access. The owner chose mTLS.
- **One CA and certificate inspection in the application**: needs a patched uvicorn protocol to
  reach the peer certificate; fragile across uvicorn releases.
- **A TLS-terminating sidecar in the backend pod** (ghostunnel, Envoy): another image to pin and a
  second process to supervise, for what three uvicorn listeners already do.
- **Built-in password login**: simpler, but no single sign-on and one shared account. The owner
  chose OIDC.
- **cert-manager as a requirement**: a cluster-wide dependency with CRDs for a demo that must run
  offline. Supported as an input (`tls.existingSecrets`), never required.
